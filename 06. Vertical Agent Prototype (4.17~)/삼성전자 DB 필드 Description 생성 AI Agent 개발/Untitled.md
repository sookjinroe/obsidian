좋은 지적이에요. 제안서 그림 정리에 매몰돼 있었어요. 사용자·청자 관점으로 다시 봐야 해요.

## RFP의 "교육: 교육이행 / 지원 / 참여" 재해석

### 단어 분석

세 단어가 병렬로 묶인 게 의미심장해요. 보통 교육 관련 RFP라면 "교육 기획·실행·평가" 같은 표현인데, 여기는:

- **이행** (perform): 교육을 받거나 시키는 행위 자체
- **지원** (support): 교육이 진행되도록 돕는 행위
- **참여** (participate): 교육 자리에 들어가는 행위

→ 이건 **"기획·설계"가 빠진 표현**이에요. 즉 **교육 컨텐츠를 만드는 게 아니라, 이미 만들어진 교육에 참여·지원·이행하는** 운영 인력의 활동을 말하는 거예요.

### 삼성전자 + KB 문서 + 76개 시스템 맥락에서 추론

**상황:**

- 국내 46개 + 해외 30개 시스템 운영
- 외부 운영사(SDS·IBM·Wipro 등)가 ITO 운영 인력 투입
- 운영 인력은 **시스템별 도메인 지식**이 필요
- 시스템은 **계속 변경**됨 (개발 변경, 솔루션 업데이트)
- 의무 교육(보안·컴플라이언스 등)도 정기적으로 발생

**그렇다면 운영 현장의 "교육" 실체는:**

#### ① 시스템 변경 발생 시 운영자가 변경 내용 학습 (이행·참여)

- ERP에 새 모듈이 추가됨 → 운영자가 그 변경 내용을 알아야 함
- 신규 기능 OJT, 변경된 절차 숙지
- **이게 가장 빈번한 "교육"**

#### ② 신규 운영자 투입 시 시스템 인수인계 (이행·지원)

- ITO는 인력 변동이 많음
- 누가 그만두면 신규 인력이 같은 시스템을 맡아야 함
- 기존 운영자가 신규자에게 시스템 지식 전달

#### ③ 의무 교육 안내·이수 관리 (지원·참여)

- 보안 교육, 개인정보 교육 등 외부 인력에게도 부과
- 운영사 인력별로 이수 여부 추적

#### ④ 운영 중 의문 발생 시 매뉴얼·동료에게 자문 (이행·지원)

- "이 화면 본 적 없는데 어떻게 처리하지?"
- 매뉴얼 검색, 선임에게 묻기

→ **요약하면: 운영자가 시스템 운영을 잘하기 위한 "지식 획득·전달" 활동**. 정식 강의 같은 느낌이 아니라 **현장 OJT 중심**.

## 실제 사용자(운영자)의 페인 포인트

이 맥락에서 **운영자가 진짜로 답답해하는 것**이 뭘까요:

### 페인 포인트 1: **"이 시스템 변경됐는데 어떻게 운영하지?"**

- 76개 시스템 중 본인이 담당 안 하던 시스템에 갑자기 투입될 수 있음
- 매뉴얼은 outdated, 릴리즈 노트만 따로 있음
- 누구한테 물어봐야 할지 모름

### 페인 포인트 2: **"전임자가 그만뒀는데 인수인계 자료가 부족"**

- 시스템 운영 노하우가 개인 머릿속에 있었음
- 신규 인력이 0에서 시작
- 며칠 동안 헤맴

### 페인 포인트 3: **"의무 교육 까먹어서 마감 임박 알림 받음"**

- 본업 바빠서 미루다가 막판에 확인
- 누락하면 컴플라이언스 이슈

### 페인 포인트 4: **"화면에서 못 본 메뉴가 떴는데 어떻게 처리하지?"**

- 변경 사항을 미리 알았어야 함
- 매뉴얼 어디 있는지 모름

## 청자(삼성전자 담당자) 관점에서 어필될 만한 것

담당자는 회의록에서 일관되게 강조해요:

- **ITO 비용 절감**
- **수치화 가능한 효과**
- **"운영사가 잘하든 못하든 시스템은 잘 돌아가게"**

이 관점에서 교육 영역의 가치:

### 청자가 흥미로워할 것 1: **운영 인력 교체 비용 절감**

- ITO 인력 turnover가 크면 인수인계 부담 커짐
- 새 인력이 빠르게 적응할수록 운영 안정성·비용 효율 ↑
- → "신규 인력이 1주일 만에 시스템 운영 가능" 같은 효과

### 청자가 흥미로워할 것 2: **시스템 변경 후 운영 안정성**

- 변경 직후가 사고 발생 빈도 높은 시기
- 변경 내용을 운영자가 빨리 숙지하면 사고 ↓
- → "릴리즈 후 운영 사고 30% 감소" 같은 효과

### 청자가 흥미로워할 것 3: **운영 노하우의 자산화**

- 운영자 개인 머릿속 노하우가 회사 자산이 됨
- 인력 의존도 줄어듦
- → "특정 인력에 의존하지 않는 운영 체계"

### 청자가 흥미로워할 것 4: **의무 교육 컴플라이언스**

- 외부 인력 의무 교육 미이수 = 컴플라이언스 리스크
- 자동 추적·독려로 100% 이수율
- → 리스크 관리 측면

## 그러면 운영 지식 Agent의 실제 가치는

### 사용자(운영자)에게:

"내가 모르는 시스템 변경, 매뉴얼, 과거 사례를 **언제든 물어볼 수 있는** 동료"

### 청자(담당자)에게:

"운영 인력이 **시스템 변경에 빠르게 적응하고**, **인수인계 비용을 줄이며**, **의무 교육 누락을 방지**하는 자동화"

## 분해를 다시 한다면

**기존 분해(A·B·C·D·E)는 너무 학술적**이었어요. 실제 운영 현장 관점으로 다시 나누면:

### 운영자의 학습 활동 4가지 (사용자 관점)

1. **변경 학습**: 시스템 변경 시 변경 내용 숙지
2. **인수인계**: 신규 운영자가 시스템 지식 획득
3. **현장 자문**: 운영 중 의문 발생 시 매뉴얼·사례 검색
4. **의무 이수**: 보안·컴플라이언스 교육 이수

### 각 활동에서 Agent가 어디까지 할 수 있나

| 활동           | Agent 위임                       | 협업                | 사람 주도        |
| ------------ | ------------------------------ | ----------------- | ------------ |
| **1. 변경 학습** | 변경 요약 자동 생성, 학습자 모드 Q&A        | 변경 영향도 큰 경우 추가 설명 | 변경 후 첫 운영 실행 |
| **2. 인수인계**  | 시스템별 매뉴얼·사례 즉시 응답, 운영 노하우 자가학습 | 핵심 노하우는 선임이 직접 전수 | 실제 트러블 시 대응  |
| **3. 현장 자문** | 자연어 질의 응답, 유사 사례 매칭            | -                 | 고난이도 판단      |
| **4. 의무 이수** | 일정 안내·미이수 독려·이수 보고             | -                 | 실제 교육 수강     |

→ **분해가 더 명확하고 사용자 관점이에요.**

③ Agent 작동 방식
**4주체:**
- 운영사 관리자
- 컨텐츠·정책 저장소
- Agent
- 운영자

**5개 흐름:**
1. 관리자 → 저장소: 컨텐츠·정책 등록·최신화
2. 저장소 → Agent: 데이터 참조
3. 운영자 → Agent: Q&A 질의 (Knox Teams)
4. Agent → 운영자: 응답·변경 요약·학습 패키지·이수 안내 (Knox Teams)
5. Agent → 관리자: outdated 노티·수정 초안 (Knox Teams)

**Agent 내부 (다이어그램 안에 키워드 수준):**
- 컨텍스트: 매뉴얼·사례·변경 공지·교육 정책·운영자 매핑
- 스킬: 검색·응답, 변경 요약·발송, outdated 감지·초안 작성, 일정 안내·독려, 이수 보고
- 도구: Knox Teams
