## 작업 목표

### 1. 왜 이 레이어가 필요한가

데이터 카탈로그는 저장하고 보여주는 것을 잘한다. 그런데 카탈로그가 못 하는 게 있다. **설명을 만드는 것.**

카탈로그는 그릇이다. 내용물을 채우는 건 카탈로그의 역할이 아니다. 지금까지 그 내용물을 사람이 수동으로 채워왔는데, 대규모 엔터프라이즈 시스템에서 수백만 개 필드를 수동으로 관리하는 건 불가능하다. 이게 이 레이어의 출발점이다.

```
[원천 데이터]  →  [우리 레이어]  →  [카탈로그 / 데이터 시스템]
                      ↑
              "의미를 만드는 엔진"
```

우리는 데이터에 의미를 부여하는 전문 레이어다. 카탈로그를 대체하는 게 아니라, 카탈로그가 혼자 할 수 없는 일을 한다. 특정 카탈로그에 종속되지 않고 어디에든 붙을 수 있는 독립 레이어로 설계한다.

---

### 2. 지금 단계가 뭔가

에이전트 1차 구현은 완료됐다. 현재는 개발자가 코드로 직접 실행하며 레거시 DB 정리 작업을 수행 중이다.

지금 단계의 목표는 **이 에이전트를 셀링 가능한 프로토타입으로 만드는 것**이다.

셀링 가능하려면 두 가지가 필요하다. 첫째, 에이전트가 백에서 돌고 결과만 받아보는 구조가 아니라 **에이전트의 실제 작업 과정이 보여야 한다.** 이 레이어의 차별점은 소스코드·용어사전·SQL 맥락까지 동원해서 의미를 찾아낸다는 것인데, 그 과정이 블랙박스면 차별점이 전달되지 않는다. 둘째, 도구가 인상적이어야 한다. 결과물이 좋다는 설명보다 직접 돌아가는 걸 보여주는 게 훨씬 강하다.

**차별점은 단일 기능이 아니라 "채우기 → 용어집 유지 → 변화 감지"로 이어지는 레이어 전체의 작업 흐름이다. 프로토는 이 흐름의 맛보기를 담는다.**

이 프로토타입은 완성된 운영 도구가 아니다. 고객이 "이런 게 가능하구나"를 체감하게 만드는 게 목적이다.

_→ 프로토 단계별 구현 계획은 `프로토타입 설계` 문서 참조_

---

### 3. 이 레이어가 갖춰야 할 것

**의미 생성 능력** — 단순히 필드명을 번역하는 게 아니라 소스코드, 용어사전, SQL 맥락, Enum 값까지 동원해서 "이 필드가 실제로 무엇인지"를 밝혀낸다. **단서가 많을수록 쉽고 적을수록 어렵다는 원칙에 따라, 값싸고 확실한 단서부터 시도하고 부족하면 비싼 단서로 에스컬레이션한다.** 이게 카탈로그가 할 수 없는 일이다.

**신뢰 생성 능력** — 만들어진 설명이 믿을 만한지 스스로 평가하고, 안 믿을 만하면 다른 방법을 시도하고, 그래도 안 되면 "모른다"고 한다. 억지로 지어내지 않는다는 것 자체가 신뢰 장치다.

**연결 능력** — 결과를 어느 데이터 시스템에도 공급할 수 있어야 한다. 특정 카탈로그에 종속되지 않는다.

**운영 지속 능력** — 한 번 만들고 끝이 아니다. **Description뿐 아니라 용어집도 함께 살아있게 유지해야 한다. 입력 자산이 정적이면 출력 품질은 반드시 저하된다.** _(→ 로드맵 참조)_

---

### 4. 로드맵 (제품 전체)

현재 단계는 **Description이 없는 필드를 생성하는 것**이다. 레거시 DB를 정리하는 1회성 작업에 해당한다.

그런데 진짜 가치는 그 다음에 있다. 필드는 한번 생기고 끝이 아니다. 스키마가 바뀌고, 컬럼 의미가 슬금슬금 바뀌고, 새 시스템이 추가되고, 기존 Description이 outdated된다. 이 변화를 추적하지 않으면 아무리 잘 만들어도 결국 다시 쓰레기 데이터가 된다.

다음 단계의 방향은 이렇다:

**1단계 (현재)** — 신규/누락 필드 Description 생성

**2단계** — 스키마 변경 감지 → 영향받는 필드 자동 재생성

**3단계** — 변경 이력 추적, 코드 참조 분석, 싱크 유지

1단계가 "채우는 것"이라면 2·3단계는 "살아있게 유지하는 것"이다. 675만 개를 만드는 것보다 그걸 살아있게 유지하는 게 더 어렵고 더 중요하다. 이 방향까지 제안할 수 있을 때 지속 가치가 생긴다.

_→ 각 단계의 제품 구성은 `제품 구성` 문서 참조_

## 논리 구조

```
카탈로그(DCS/Atlan/MDM)가 있어도
  → 설명이 없으면 데이터를 신뢰할 수 없고
  → 신뢰할 수 없으면 AI 분석에 쓸 수 없고
  → AI 분석에 못 쓰면 카탈로그를 도입한 이유가 없어진다

우리 레이어는
  → 설명을 만들고
  → 그 설명을 신뢰할 수 있게 평가하고
  → 지속적으로 최신 상태로 유지하고 (Description + 용어집)
  → 어느 카탈로그에도 공급할 수 있다
```

## 관련 문서

- **제품 구성** — 모듈 구조, 추론 엔진, 용어집 상태별 작동, 판매 티어, 경쟁 커버리지
- **프로토타입 설계** — 시연 시나리오, 프로토 4단계 로드맵, UI 구성
- **프로토타입 구성 개요** — 프로토 1차 범위 상세
