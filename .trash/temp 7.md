맞아요. 순서가 그게 맞아요. "이런 게 필요해요" 샘플을 먼저 만들면 개발자가 "이 중에 지금 할 수 있는 것, 나중에 할 것"을 판단할 수 있으니까요.

그럼 Observability 설계를 두 레벨로 나눠서 정리해볼게요.

---

## 레벨 1 — 배치 실행 중 보이는 것 (흐름 뷰)

배치로 여러 컬럼을 처리하는 동안 실시간으로 쌓이는 뷰예요. 한 컬럼당 한 줄이 생겨나요.

사용자가 보는 것:

```
테이블명: ORDER_ITEM                              진행 23/148

컬럼명              결과                    Confidence  소요시간
──────────────────────────────────────────────────────────────
cust_id         고객식별번호               ● high      0.3s   ✓
ord_dt          주문등록일자               ● high      0.4s   ✓
disc_rt         할인율정보                 ● medium    1.2s   ✓
flg_tax_exmp    과세면제구분코드            ● low       2.1s   검토필요
stat_cd         처리중...                  -           -      ...
```

**이걸 위해 파이프라인이 남겨야 할 것 (LLM 비용 없음):**

- 컬럼명
- 생성된 Description (한글/영문)
- Confidence 판정 (LLM structured output에서)
- 소요시간
- 완료/오류 상태

---

## 레벨 2 — 단건 드릴다운 (검토 화면에서 클릭 시)

`flg_tax_exmp` 행을 클릭했을 때 펼쳐지는 뷰예요. 여기서 "뭘 봤고 왜 그렇게 판단했는지"가 드러나요.

사용자가 보는 것:

```
[컬럼] flg_tax_exmp  |  테이블: ORDER_ITEM  |  시스템: 주문관리

── 생성 결과 ─────────────────────────────────────────────────
한글: 과세면제구분코드
영문: Tax Exemption Classification Code
T: 과세면제  /  P: 구분  /  F: 코드

Confidence: ● low
이유: Enum 값 존재하나 P(목적) 추론에 불확실성 있음

── 처리 과정 ─────────────────────────────────────────────────
① 91개 표준항목 매핑    → 불일치 (유사항목: 없음)

② 용어집 조회           → "flg_tax_exmp" 검색
                          결과: "면세여부" 1건 매칭
                          → T(과세면제) 확보

③ 소스코드 분석         → Enum 발견
                          TaxExemptionType.java
                          Y=일반면세 / N=과세 / P=부분면세 / X=해당없음
                          → F(코드) 확보, 4가지 값 존재 확인

④ LLM 추론 (Level 2)   → P(목적)를 "구분"으로 추론
                          근거: Enum 패턴 + 컬럼명 접미사 flg

── 원본 데이터 ──────────────────────────────────────────────
컬럼 타입: character(1)    기존 Description: (없음)
샘플 값:   Y, N, P, X
```

**이걸 위해 파이프라인이 남겨야 할 것:**

|단계|캡처할 데이터|비용|
|---|---|---|
|mapping_check|매핑 결과 (Y/N), 유사항목|코드레벨|
|fetch_tools (용어집)|검색 쿼리, 매칭 결과|코드레벨|
|fetch_tools (소스코드)|파일명, 발견된 Enum/i18n 내용|코드레벨|
|llm_gen|T/P/F 분리값, Confidence, 이유코드, 추론 Level|structured output 필드 추가|

---

## 레벨 3 — 캡처 안 해도 되는 것

- LLM의 내부 thought process 전문
- 검색에서 매칭 안 된 후보 목록 전체
- 노드 내부의 모든 중간값

---

이 스펙을 개발자에게 보여주면서 "레벨 1은 지금 바로 가능한가, 레벨 2에서 각 항목별로 현재 State에 남기고 있는지"를 물어볼 수 있어요. 처리 과정 ①~④의 자연어 서사는 UI에서 조합하는 거고, 파이프라인은 raw 데이터만 남기면 돼요.

이 방향으로 개발자 협의 자료를 만들면 될까요?
