## 이 문서가 뭔가

삼성 DX 필드 디스크립션 프로젝트에서 **"어떤 방법으로 필드 설명을 잘 만들 수 있는가"**를 검증하기 위해 세운 가설 목록이에요. H-01부터 H-24까지 총 24개.

각 가설은 **"이 데이터를 이런 방식으로 활용하면 품질이 올라갈 것이다"**는 형태예요.

### 1. 아키텍처 (H-01, H-22)

**H-01**: Single Agent vs. Multi Agent 효율성 비교

- "에이전트 하나로 할지, 여러 개로 나눌지 어떤 게 더 낫나?"
- Single Agent = 대상·목적을 한 에이전트가 처리
- Multi Agent = 대상·목적을 별도 에이전트로 분리
- 가설: Single Agent가 더 동등한 품질에 효율이 높을 것

**H-22**: 비동기 병렬 처리

- "여러 필드를 동시에 처리하면 속도가 얼마나 빨라지나?"
- 가설: 비동기 병렬 처리 시 생성 속도 향상

---

### 2. 추론 전략 (H-03~H-07, H-21)

이 군이 **"에이전트에게 어떻게 지시하는가"**를 다뤄요.

**H-03**: 침묵(Silence) 전략

- 컨텍스트가 불충분할 때 억지로 생성하지 말고 **"판단 불가"를 출력**하게 하면 오류율이 줄어들 것
- 모르면 모른다고 하게 만드는 전략

**H-04**: 계층적 컨텍스트 적용

- 기업→시스템→테이블→필드 순서로 **위에서 아래로 맥락을 전달**하면 정확도가 올라갈 것
- "이 필드는 이 시스템 안에 있고, 그 시스템은 이런 목적을 가진다"는 구조를 에이전트에게 줌

**H-05**: 금지 규칙 기반 프롬프트

- "이렇게 쓰지 마라"는 규칙을 명시하면 잘못된 추론 패턴이 줄어들 것
- 예: "필드명을 그대로 번역하지 마라", "한 문장 이상으로 쓰지 마라" 등

**H-06**: 컨텍스트 충분도 기반 단계별 추론

- 컨텍스트가 얼마나 있느냐에 따라 추론 수준을 Level 0~3으로 나눠서 적용
- 정보가 없으면 보수적으로, 정보가 풍부하면 깊게

**H-07**: AI Agent 추론 원칙 통합 적용

- 개별 전략(침묵, 계층적, 금지, 단계별)을 **조합해서 하나의 통합 버전**으로
- 관리 용이성 측면에서 통합이 유리할 것

**H-21**: 프롬프트 압축기법 활용

- 불용어 제거, 구조화 포맷, 약어 정의, JSON 형식 지시 등 **프롬프트를 압축**하면 생성 일관성이 높아질 것

### 3. 데이터 소스 (H-02, H-08~H-20, H-23~H-24)

이 군이 가장 많아요. **"어떤 데이터를 에이전트에게 주면 더 잘 만드나"**를 다뤄요.

**기본 데이터:**

**H-02**: DB 메타 + 샘플데이터 기반 생성 (Baseline)

- 테이블·컬럼 정보 + 샘플 값만으로 기준선 품질 확보
- 모든 가설의 출발점. 이것 없이는 비교가 안 됨

**H-08**: 시스템 도메인/산업군 정보 추가

- "이 시스템은 공급망 관리 시스템이다"는 정보를 주면 정확도가 올라갈 것

**H-09**: 비즈니스/도메인 용어사전 활용

- 업계 표준 용어집을 주면 일관성이 올라갈 것

---

**소스코드 계열 (H-12~H-20, H-23):**

이 부분이 시뮬레이션의 **H-23 하이라이트**와 직접 연결돼요.

**H-12**: DTO/VO 변수명 추출

- 소스코드 안에서 이 컬럼을 담는 객체의 변수 이름이 컬럼명과 다를 수 있음
- 그 변수명을 보면 의미 파악 가능

**H-13**: SQL 쿼리 맥락 분석

- SELECT, INSERT, UPDATE에서 이 컬럼이 **어디에 쓰이는지** 패턴 분석
- WHERE 조건, JOIN 관계, 집계 함수 등이 힌트

**H-14**: ORM 컬럼매핑 분석

- @Column, @JoinColumn, ResultSet 매핑에서 컬럼과 객체 필드의 관계 파악

**H-15**: 주석 추출

- 코드 라인 또는 관련 메서드의 JavaDoc, 인라인 주석에서 의미 추출

**H-16**: 다국어 리소스(i18n) 활용

- messages.properties 같은 파일에서 컬럼명과 연관된 **화면 표시 라벨** 추출
- 사용자에게 노출되는 이름이니까 가장 직관적인 의미를 담고 있음

**H-17**: Enum 분석

- 이 컬럼 값과 매핑되는 Enum 클래스가 있다면 상수명과 설명으로 의미 파악
- 바로 이게 시뮬레이션의 `flg_tax_exmp` Y/N/P/X 케이스예요

**H-18**: F/E Label

- 화면에 표시되는 라벨을 활용
- 아까 제가 시뮬에서 "용어사전"으로 잘못 표현했던 게 사실은 이거예요

**H-19**: Git 커밋/Jira 이슈 분석

- 이 컬럼과 관련된 변경 사항의 커밋 메시지나 Jira 이슈를 활용
- 컬럼이 왜 만들어졌는지, 어떤 맥락에서 변경됐는지 파악 가능

**H-20**: I/F 문서 활용

- 타 시스템 연계 인터페이스 문서에서 이 컬럼이 어떻게 쓰이는지 파악

**H-23**: Keyword 기반 소스코드 분석

- 파서를 개발하지 않고 **필드명을 키워드로 소스코드 내 연관 텍스트**를 찾음
- SQL Alias, ORM, i18n, Enum, F/E Label 등을 포함
- 아까 시뮬에서 "소스코드를 뒤집는다"고 표현한 게 이거예요 — 근데 실제 방식은 파서 없이 키워드 매칭

**H-24**: 컬럼 데이터 타입 정보 추가

- jsonb, character varying, integer 등 타입을 주면 포맷(F) 접미사 정확도가 높아짐
