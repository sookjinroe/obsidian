## 1. 제품 포지션

**데이터 카탈로그 위에 얹는 AI 레이어.**

카탈로그를 대체하지 않는다. 카탈로그가 못 하는 세 가지 지능을 제공한다.

1. **의미 생성** — 필드가 실제로 무엇인지 밝혀낸다
2. **신뢰 생성** — 만들어진 설명이 믿을 만한지 스스로 평가한다
3. **지속 유지** — Description과 용어집을 살아있는 상태로 관리한다

어느 카탈로그에도 붙을 수 있는 독립 레이어로 설계되며, 특정 카탈로그 벤더에 종속되지 않는다.

## 2. 추론 엔진 (5레벨 에스컬레이션)

Description 생성은 단계별 접근을 취한다. 단서가 많을수록 쉽고, 적을수록 어렵다. 비용이 낮고 확실한 단서부터 시도하고, 부족하면 다음 레벨로 에스컬레이션한다.

|레벨|원리|사용 데이터|Confidence|
|---|---|---|---|
|**L0 — 자산 재활용**|타 시스템에 같은 컬럼 설명이 이미 존재|기존 Description DB|높음|
|**L1 — 용어집 조립**|컬럼명·맥락에서 의미를 용어집과 매핑|비즈니스 용어집|높음|
|**L2 — 구조 힌트**|스키마·샘플값·타입으로 추론|DB 메타데이터·샘플|중간|
|**L3 — 코드 맥락**|소스코드에서 Enum·라벨·변수명 발굴|코드 저장소|중간|
|**L-1 — 침묵**|단서 없음 → "판단 불가" 선언|—|N/A|

**L-1의 존재가 이 엔진의 신뢰 장치다.** 억지로 만들지 않는 것 자체가 고객이 결과를 믿을 수 있는 근거가 된다.

레벨 간 이동은 양방향이다. L3에서 단서를 찾다가 상위 레벨에 매핑되는 걸 발견하면 승격시킨다.

**매칭은 알고리즘이 아니라 LLM 추론이다.** 전통적인 fuzzy matching·문자 유사도 방식이 아니라, LLM이 컬럼명·테이블 맥락·스키마·소스코드를 한 번에 읽고 종합 해석한다. 그래서 컬럼명이 암호화돼 있거나 용어집이 부실해도 주변 맥락이 충분하면 추론이 작동한다.

## 3. 용어집 상태별 작동 방식

조직마다 용어집 성숙도가 다르고, 이에 따라 추론 엔진의 동작이 달라진다. **타깃 시장의 대부분은 Case 2·3**에 해당하므로 제품 설계가 이 상태들을 모두 커버해야 한다.

### Case 1 — 용어집 충분

조직이 오랫동안 거버넌스 해온 곳. 수백~수천 개 term이 유의어·약어까지 정리되어 있음.

- 시장 분포: 소수 (10~20%, 금융·보험 등 규제 산업)
- 주 작동: L1(용어집 조립)이 대부분 성공
- 제품 가치: 속도와 일관성

### Case 2 — 용어집 거의 비어 있음

거버넌스 미도입 조직. term이 수십 개 수준이거나 없음.

- 시장 분포: 상당수 (30~40%, 스타트업·중견기업)
- 주 작동: L1 실패 → L3(소스코드)까지 자주 내려감, **용어집 Bootstrap이 선행 필수**
- 제품 가치: "시작 자체를 가능하게 함" — 용어집 구축 시간을 수개월에서 며칠로 단축

### Case 3 — 일부 비어 있음 (가장 현실적)

기본 term은 있는데 새 시스템 추가, 도메인 확장, 약어 매핑 부실.

- 시장 분포: 다수 (50~60%)
- 주 작동: 세 레벨 모두 활성, Confidence 분포가 다층적
- 제품 가치: "살아있게 유지" — 변화에 맞춰 용어집·Description 지속 갱신

## 4. 핵심 모듈

### M1. Description Engine

의미 생성의 핵심. 내부에 세 개의 서브 에이전트가 협력한다.

**Vocabulary Builder** — 용어집 구축·갱신

- 소스코드(Enum·i18n·변수명·주석)와 컬럼명 패턴에서 용어 후보 발굴
- 약어-확장 쌍(AEP) 자동 식별
- 용어집이 없는 Case 2에서 부트스트랩 담당
- Case 3에서 운영 중 자동 보강 담당

**Term Linker** — 컬럼↔용어 매핑

- LLM이 컬럼 맥락을 읽고 용어집 term과 연결
- 매핑 신뢰도 점수 부여

**Description Composer** — Description 생성

- 매핑 결과 + 여러 레벨 단서를 종합해 Description 작성
- Confidence와 출처 메타데이터 기록
- 내부 구조는 대상(Target) + 목적(Purpose) + 포맷(Format) 분해, 출력 포맷은 조직 템플릿에 맞춰 변환

**공통 기능**

- Multi-level 추론 엔진 (L0~L3, L-1)
- 조직별 템플릿 커스터마이징
- 다국어 생성 (한/영 기본, 확장 가능)
- 출처 역추적

### M2. Context Enricher

컬럼 단위를 넘어선 맥락 생성.

- 테이블 README 자동 생성
- 도메인 태깅 (매핑 어려운 영역 자동 분류)
- 관련 컬럼 그룹핑 (조인·참조 패턴 기반)
- 사용량 기반 우선순위 큐

### M3. Sync Manager

"채우기"가 아닌 "살아있게 유지"의 실체. 제품의 장기 가치가 집중되는 모듈.

- 스키마 변경 감지 → 영향 범위 계산 → 재생성 큐
- 소스코드 변경 감지 → 관련 설명 갱신
- 값 분포·사용 패턴 변화 감지 → "의미 drift" 알람
- 변경 이력 추적

### M4. Quality Inspector

자동 생성된 결과를 고객이 믿을 수 있게 만드는 장치.

- LLM-as-a-Judge 자동 검증
- Grounding check (출처 실재성 확인)
- 규칙 기반 후처리
- Low confidence 항목 HITL 큐 라우팅
- 검토 결과 피드백 → 조직별 맞춤 개선

## 5. 공통 인터페이스 계층

이 계층이 "카탈로그에 종속되지 않는 독립 레이어"의 실체다.

### Source Connectors — 원천 데이터 접근

- DB 커넥터 (PostgreSQL·Oracle·Snowflake·BigQuery 등)
- 코드 저장소 커넥터 (Git·SVN·엔터프라이즈 저장소)
- 카탈로그 API 커넥터 (읽기 전용 — 리니지·사용량·기존 설명 수집)
- 메타데이터 시스템 커넥터 (ETL 도구·MDM 등)

원칙: **카탈로그가 있으면 먼저 뒤지되, 없어도 동작한다.** 카탈로그 의존으로 설계하면 조직마다 카탈로그 성숙도가 달라 어떤 곳에선 잘 되고 어떤 곳에선 안 된다. 원천 소스에 직접 접근 가능해야 하며, 카탈로그는 "이미 가공된 게 있으면 먼저 쓰는" 보조 출처로 위치.

### Input Assets — 입력 자산 관리

- 용어집 (CSV 업로드 / 카탈로그 동기화 / 직접 편집)
- 조직별 출력 템플릿

### Output Adapters — 결과 공급

- 주요 카탈로그별 어댑터 (DCS·Collibra·Atlan·DataHub·Informatica)
- 범용 export (JSON·CSV·REST API)
- 자연어 쿼리 엔진 전용 피드

### Observability & Governance UI

두 가지 맥락에서 사용되며 성격이 다르다.

**프로토타입 맥락 (셀링 도구)**

- 실시간 추론 경로 시각화
- 차별점 체감용

**운영 맥락 (Governance Console)**

- 대량 처리 결과의 검색·필터링
- Low confidence 항목 검토 워크플로우
- 각 설명의 출처 역추적
- 변경 이력 및 drift 비교 뷰
- 감사·책임 추적

같은 기반 데이터(추론 경로·출처·confidence)를 공유하지만 **프로토는 "시연용 스트리밍 뷰", 운영은 "관리자 콘솔"** 로 목적이 나뉜다.

## 6. AI-Ready 출력 구조

M1이 생성하는 설명은 단순 텍스트가 아니다. 자연어 쿼리 엔진이 즉시 소비할 수 있는 구조화된 출력을 만든다.

- 대상(Target) + 목적(Purpose) + 포맷(Format) 분리 저장 (내부 추론 구조)
- 출력 포맷은 조직 템플릿에 따라 변환
- 동의어·값 정의·Enum 포함
- Confidence와 출처 메타데이터
- 한/영 병기

T+P+F는 출력 형태가 아니라 **내부 추론 구조**다. 조직마다 요구하는 출력 포맷이 다르므로(간결형 / 서술형 / 한국 공공 표준 등), 같은 내부 구조를 유지한 채 포맷만 변환한다. 이게 자유 텍스트로 바로 생성하는 Atlan 방식 대비 구조적 강점이다.

자연어 쿼리 엔진은 이 구조화된 정보를 통해 사용자 자연어 표현을 컬럼으로 정확히 매핑한다. 사용자가 "면세"라고 말하든 "세금 안 내는"이라고 말하든 같은 컬럼에 도달할 수 있다.

## 7. 판매 티어

|티어|포함 모듈|타깃 고객|모델|
|---|---|---|---|
|**Starter**|M1 + Observability UI|레거시 DB 정리 1회성|프로젝트성 납품|
|**Standard**|M1 + M2 + M4|자연어 SQL 도입 중인 조직|초기 구축 + 정기 갱신|
|**Enterprise**|M1 + M2 + M3 + M4|운영 레벨 지속 관리|구독 / 지속 계약|

Starter는 프로젝트성·1회성이고, Enterprise가 구독 계약이다. 레거시 카탈로그를 쓰면서 자연어 SQL 엔진을 도입 중인 고객은 Standard부터 시작해 Enterprise로 확장하는 경로가 자연스럽다.

## 8. 경쟁 커버리지

시장의 AI 카탈로그 솔루션(대표적으로 Atlan)은 쿼리 로그·리니지·컬럼 명명 패턴을 주요 시그널로 사용한다. "사람들이 이 컬럼을 어떻게 쓰는가"를 관찰해 LLM이 종합 해석해 설명을 만드는 방식이다.

본 제품도 같은 LLM 에이전트 아키텍처를 취하지만, **활용하는 시그널의 범위**가 다르다. 아틀란이 카탈로그 안의 시그널에 집중한다면, 본 제품은 거기에 더해 **소스코드까지 뒤진다**. 이것이 레거시 엔터프라이즈 환경(쿼리 로그 산발적, 리니지 미관리, 문서 빈약)에서 결정적 차이를 만든다.

### 커버리지 매트릭스

|영역|본 제품|Atlan 방식|
|---|---|---|
|타 시스템 자산 재활용|○ (L0)|✗|
|용어집 조립|○ (L1)|○|
|컬럼명·스키마 추론|○|○|
|소스코드 정적 분석 (Enum·라벨)|○ (깊음, L3)|△ (얕음)|
|용어집 자동 구축·갱신|○ (Vocabulary Builder)|○ (Lexis)|
|쿼리 로그 기반 사용 패턴|△ (연결 가능)|○ (Scout)|
|리니지 기반 추론|△ (연결 가능)|○|
|테이블 단위 README|○ (M2)|○ (Doc)|
|사용량 기반 우선순위|○ (M2)|○ (Scout)|
|자동 검증 + HITL 루프|○ (M4)|✗|
|출처 역추적 UI|○|△|
|지표 충돌 감지|✗ (스코프 밖·거버넌스 영역)|○ (Sage)|
|데이터 품질 평가|✗ (스코프 밖·타 레이어)|○ (Vera)|
|온톨로지·지식 그래프|△ (M3 진화형)|○ (Orion)|

**요약**

- 같은 LLM 에이전트 아키텍처
- 소스코드 시그널의 깊이로 차별화 (Case 2·3에서 결정적)
- 자동 검증·출처 역추적에서 고유 영역 보유
- 의도적 제외 영역 명확 (Sage·Vera — 타 레이어 문제)

## 9. 핵심 메시지

> **카탈로그가 아니라, 카탈로그의 지능이다.**
> 
> 카탈로그를 바꾸라고 하지 않는다. 레거시 그대로 두고 그 위에 AI-ready 지능을 얹는다.
> 
> 의미를 만들고, 만든 것을 신뢰할 수 있게 평가하고, 변화에 맞춰 살아있게 유지하고, 어느 카탈로그에도 공급한다.
