## 1. 회의 개설 맥락 및 담당자 뉘앙스

양경호 프로는 회의 시작 시 다소 부담스러워하는 기색을 보이며 다음과 같이 전제함:

- 원래 문의는 서면으로 받아 서면으로 답변하기로 공지했으나, 에스코어 측이 먼저 연락해와 비공식 미팅을 열었음
- *"파트장님 허락 없이 임의로 진행한다"*고 언급 — 즉, 이 회의 자체가 공식 채널 밖의 비공개 소통
- 과제가 크다 보니 너무 구체적인 정보 제공은 스스로 제한하겠다고 사전 고지
- 다른 입찰 후보 업체들도 동일하게 정보가 제한된 상황이라고 밝힘

**→ 에스코어가 기존 운영사로서 선제적으로 정보를 확보한 자리이며, 이 내용은 타 업체에는 공유되지 않은 비공식 정보임**

## 3. 사업 구조 — 1번 과제 vs 2번 과제 (회의에서 구체화된 내용)

RFP에는 단순히 "별도 RFP 예정"으로만 기재되어 있으나, 회의에서 훨씬 구체적으로 설명됨.

|구분|1번 과제 (현재 RFP)|2번 과제 (미출시)|
|---|---|---|
|핵심 역할|AI 영역 발굴 + 에이전트 구축 + 평가체계 + 무인화 시범운영|1번 과제 산출물을 국내·해외 시스템에 확산 적용|
|발주 대상|공개 경쟁입찰 (현재 진행 중)|ITO 운영 업체 대상 별도 RFP|
|협업 구조|솔루션 기반 시스템의 요구사항을 2번 과제로부터 수신|1번 과제 개발 에이전트를 수령 후 적용, 효과 확인 후 피드백|
|에이전트 개발 주체|**1번 과제에서 단일 주체가 전담**|에이전트 적용 및 피드백만 담당|

> **내부 논쟁 포인트:** "에이전트 개발 자체를 2번 과제에서 하는 게 맞지 않냐"는 내부 의견도 있었으나, 최종적으로 개발은 1번 과제 단일 주체가 담당하는 것으로 의사결정이 완료됨.

## 5. RFP가 러프하게 작성된 이유 (담당자 직접 발언)

> **양경호 프로 발언 (원문에 가까운 정리):** "담당자 입장에서는 최대한 구체적으로 쓰는 게 준비하시는 분들께 도움이 될 것 같다고 생각했는데, 윗분들께서 너무 구체적으로 적으면 오히려 그 포커스에만 맞춰서 더 넓은 영역을 검토하지 못할 것 같다는 의견을 주셔서, 의도적으로 조금 러프하게 기재된 면이 있습니다."

**→ 시사점:** RFP의 모호함은 의도된 것. 제안사가 RFP 범위를 넘어 더 넓고 창의적인 시각으로 제안해주길 기대하는 구조. 포커스를 넓게 가져가야 유리함.

**→ 에이전트 간 Workflow 자동화가 가장 즉각적이고 구체적인 개선 과제임. 이 부분에 대한 명확한 설계 제안이 핵심 차별화 포인트.**

## 8. 무인화 시범운영 (담당자의 실제 생각)

RFP에는 조건만 기재되어 있으나, 회의에서 담당자의 실제 기대치와 고민이 드러남.

### 8-1. 대상 시스템 선정 기준 (담당자 발언 정리)

> "원래 제가 처음에는 VOC가 거의 없는 시스템을 선정하겠다고 썼는데 너무 분명하다 해서, 그나마 운영인력 1인 이하라고 표현했습니다. 실제로 SS 정규 인력 한 분이 여러 개 시스템을 관리하시는 경우도 있고, 개발 티켓이 전혀 없는 경우도 있어요."

- **사실상의 기준:** VOC 없음 + 개발 티켓 없음 + 모니터링 중심 운영
- 시스템 수: **국내 1~2개** (추후 별도 협의)

### 8-2. 담당자가 생각하는 무인화 시나리오 (확정 아님 — 아이디어 공유)

> "이 시나리오는 그냥 제 개인적인 담당자 생각입니다. 요거 딱 여기에 국한하지 않으셨으면 좋겠습니다."

1. 시스템 자동 복구 → 운영자 알림 (기본 시나리오)
2. 데이터 조회·추출 요청 자동 처리 (중간 시나리오)
3. **간단한 기능 개발 요청까지 자동 처리** (최상위 시나리오 — 담당자는 "욕심을 내본다면" 수준으로 표현)

> **담당자 솔직한 언급:** "저도 너무 막막해요, 사실은. AI 기술 발달이 굉장히 빠르다고는 하나 요구사항이 들어오면 개발하고, 검증하고, 자동 배포하고, 문제없이 동작하는 부분까지는 저는 개인적으로는 좀 과하다는 생각이 들고..."

**→ 무인화 범위는 제안사가 역으로 제시하는 방식. 너무 공격적인 수치보다 현실적이고 단계적인 접근이 더 신뢰를 줌.**

## 9. AI 효과 측정 — 가장 어려운 핵심 과제

담당자가 이 부분에서 가장 많은 고민을 털어놓음.

### 9-1. 현재 측정 방식

- **A/B 테스트:** 동일한 SR을 수작업으로 처리한 시간 vs AI 도구 활용 시간의 차이를 효과로 정의
- **2025년 5월 파일럿 이후 현재까지 이 방식 이외에 객관적 수치화 방법을 찾지 못한 상태**

### 9-2. 담당자 발언 (핵심)

> "A/B 테스트 외에는 찾지를 못했어요. 아직까지도. 어떻게든 이걸 안 할 수 있는 방법은 없을까라고 SS에서 고민하고 계시고 저희도 계속 고민하고 있는데 답을 찾지 못하고 있는 상황입니다. 그래서 요즘 뭔가 좋은 해안이 있으시면 제안해 주시면 아주 큰 플러스가 될 것 같습니다. 제일 힘들거든요."

### 9-3. 이 과제의 궁극적 목표 (담당자가 직접 언급)

> "큰 형님들이 이 과제가 최종적으로 비용이 ITO 계약 비용에서 빠지지 않으면, 결과적으로 이 과제는 진짜 아무 의미가 없게 되는 과제입니다. 충분히 인지하시겠지만."

**→ 이 과제의 존재 이유는 ITO 계약 비용 절감. 효과를 객관적으로 수치화하여 운영사가 납득하게 만드는 것이 1번 과제의 핵심.**

### 9-4. 목표수준 제시 방식에 대한 가이드

> "있는 그대로 말씀해 주시면 좋을 것 같아요. 뭐 예를 들어서 정확하게 수치라고 써달라고 했지만 레인지를 들어서 10에서 20이다, 이렇게 표현하셔도 될 것 같고. 딱히 정답은 없습니다만, 실현 가능성을 좀 보겠다 정도로 봐주시면 좋을 것 같습니다."

## 10. 업무 비중 및 개선 전략

### 10-1. 비중의 의미

- **근거:** 에스코어와의 ITO 비용 정산 시 사용한 30여 개 시스템의 52개 액티비티 기반 업무 비중
- 특정 시스템별 특성이 아닌 **전체 평균적인 비중**
- 삼성전자와 에스코어가 상호 협의하여 확정한 수치

### 10-2. 평가 메커니즘

> "각 단계별로 목표 수준을 적어주시면, 비중을 곱해서 하나의 숫자로 만들어내려는 것이 저희 목표입니다."

- 비중 × 목표수준(%) = 단일 점수로 환산 → 업체 간 비교
- **비중이 높은 항목을 개선할수록 ITO 비용 절감 효과 극대화**

### 10-3. 비중 기준 전략적 우선순위

|우선순위|항목|비중|전략적 의미|
|---|---|---|---|
|1순위|시스템 모니터링|**29%**|가장 임팩트가 큰 영역. 기개발 에이전트 존재. 고도화 방향 명확히 제시 필수|
|2순위|문의대응|**18%**|챗봇·ITSM 연계로 자동화 가능성 높음|

## 11. SonarQube·Git-Patch MCP 연계 — 예시임을 명확히 함

## 16. 제안 전략 시사점 요약

### 반드시 강조해야 할 요소

1. **AI 개선 효과의 객관적 수치화 방법론** — A/B 테스트를 넘는 새로운 측정 방법 제안 시 최대 차별화 포인트 ("제일 힘들다"고 직접 언급)
2. **ITO 계약 비용 절감과의 직접 연계 방안** — 과제의 존재 이유이자 최종 KPI
3. **에이전트 간 Workflow 자동화** — 현재 수동 copy-paste 구조를 자동화하는 것이 즉각 실현 가능한 핵심 개선
4. **비중 높은 항목 집중 공략** — 시스템 모니터링(29%), 문의대응(18%) 위주로 임팩트 극대화 전략 제시
5. **외부 모델 교체 용이한 구조** — 2026년 하반기 외부 모델 도입 예정을 고려한 유연한 아키텍처

### 자유 제안이 가능한 영역

- IntelliJ Continue Plugin을 다른 오픈소스로 대체 제안 가능
- IDE 호환성 확장 (이클립스 등 구형 IDE 지원)
- 테스트 시나리오 생성에서 테스트 실행 자동화로 확장
- 무인화 범위는 제안사가 역으로 제시하는 방식 — 단계적 시나리오 구성 권장
- MCP 연계 대상 툴 선택은 제안사 판단

### 주의사항

- 목표 개선율은 레인지 표기(예: 10~20%) 허용 — 허무맹랑한 단일 수치보다 실현 가능성 중시
- AppZen(OutSystems) 기반 포털 수정·개발 역할 및 비용도 반드시 포함
- Gauss 대체 플랫폼 제안 시 차별화 논거 필수, 무조건적 신규 플랫폼 도입 제안은 역효과 가능
- ABAP·SFDC 등 솔루션별 특성을 Java 대비 구체적으로 기술 시 가점
