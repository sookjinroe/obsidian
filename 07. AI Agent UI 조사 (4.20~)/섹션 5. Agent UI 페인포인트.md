## 페인포인트 1. 불투명한 실행 → 투명성 UI 설계 필수

**사용자 경험:** AI가 이유 없이 행동할 때 사용자는 추측하게 된다. 행동이 임의적으로 느껴진다. 결과가 단절된 것처럼 보인다. 시스템이 신중하게 행동했는지 무작위로 행동했는지 판단할 수 없을 때 신뢰는 빠르게 무너진다. [UXmatters](https://www.uxmatters.com/mt/archives/2025/12/designing-for-autonomy-ux-principles-for-agentic-ai.php)

**기획 고려사항:** "얼마나 보여줄 것인가"를 단일 답으로 결정하면 안 됩니다. 고위험·비가역 작업에는 추론 단계를 노출하고, 반복적·저위험 작업은 요약만 보여주는 **위험도 기반 투명성 레벨**을 설계해야 합니다.

**개발 고려사항:** AG-UI의 `TOOL_CALL_START`, `TOOL_CALL_RESULT` 이벤트를 UI에 연결하는 것만으로도 기본 투명성은 확보됩니다. 더 나아가면 LangSmith, Langfuse 같은 관찰 가능성(Observability) 레이어와 연동해 사용자에게 "왜 이 결정을 했는가"를 보여주는 시각적 추론 트레일을 제공할 수 있습니다.

## 페인포인트 2. 대기 시간의 불안감 → 진행 상태 내러티브 설계

**사용자 경험:** Agent가 장시간 실행될 때 사용자는 "멈춘 건지 작동 중인지"를 모릅니다. 빈 화면이나 스피너만 보여주면 신뢰가 떨어집니다.

**기획 고려사항:** 대기 시간을 서사적 기회로 전환해야 한다. 에이전트가 진행 중임을 보여주고("에이전트 알파가 인사이트를 합성하는 중..."), 지연을 설명하고("공급업체 계약 분석 중..."), 중간 결과나 에이전트 활동 지표를 제공한다. 사용자가 기다려야 할 때도, 수동적으로 느껴질 필요는 없다. [World Economic Forum](https://www.weforum.org/stories/2025/08/rethinking-the-user-experience-in-the-age-of-multi-agent-ai/)

**개발 고려사항:** AG-UI의 `RUN_STARTED`, `TOOL_CALL_START` 이벤트를 단순 로딩 표시가 아니라 **자연어 서술형 상태 메시지**로 변환하는 UI 레이어가 필요합니다. "분석 중..."이 아니라 "계약서 47개 중 23번째 문서를 검토하고 있습니다."처럼 구체적일수록 불안감이 감소합니다.

## 페인포인트 3. 실수 복구 불가 → Undo/Rollback을 제품 핵심 기능으로

**사용자 경험:** Agent가 비가역 작업(파일 전송, 데이터 수정, 외부 API 호출)을 실행한 뒤 되돌릴 방법이 없으면, 사용자는 그 다음부터 Agent에게 중요한 작업을 위임하지 않습니다. 신뢰를 쌓을 기회가 없어집니다.

**기획 고려사항:** 영구적이고 읽기 쉬운 액션 감사 로그와 모든 가능한 액션에 대한 눈에 띄는 Undo 버튼은 궁극적인 안전망이다. 자율성 부여의 인지된 위험을 크게 낮춘다. 비가역적이 되는 시점(예: 환불 불가 예약의 경우)에 대한 시간 창을 UI가 명확히 전달해야 한다. [Smashing Magazine](https://www.smashingmagazine.com/2026/02/designing-agentic-ai-practical-ux-patterns/)

**개발 고려사항:** 되돌릴 수 있는 작업과 없는 작업을 사전에 명확히 분류하고, 각 작업의 `rollback_available` 여부와 `rollback_deadline`을 UI에 노출하는 데이터 구조 설계가 선행되어야 합니다. 이것은 UX 문제가 아니라 백엔드 설계 문제입니다.

## 페인포인트 4. 인터페이스 낯섦 → 진입점 설계와 온보딩

**사용자 경험:** 기존 소프트웨어 패턴(버튼, 탭, 메뉴)에 익숙한 사용자에게 "프롬프트만 있는" Agent UI는 "어디서 시작해야 하는지 모르는" 막막함을 줍니다.

**기획 고려사항:** 빈 프롬프트 창으로 시작하지 마세요. CoCounsel의 Skill 갤러리처럼 **타일 기반 태스크 진입**, Cursor의 **슬래시 커맨드**처럼 맥락 내 제안, 혹은 `스타터 프롬프트 라이브러리`처럼 첫 상호작용을 구조화하는 설계가 낯섦을 줄입니다.

**개발 고려사항:** 온보딩 단계에서 사용자가 Agent의 "능력 범위"를 빠르게 파악할 수 있는 **기능 발견성(Capability Discovery)** UI를 설계해야 합니다. Agent가 무엇을 할 수 있는지 모르면 쓰지 않습니다.

## 페인포인트 5. 통제권 상실감 → 자율성 조절 컨트롤

**사용자 경험:** 자율성이 높을수록 사용자는 "내가 아니라 AI가 결정하는 것 같다"는 불안을 느낍니다. 특히 엔터프라이즈 환경에서 업무 책임 구조와 충돌할 때 더 심해집니다.

**기획 고려사항:** 슬라이더 또는 모드 선택기를 통해 사용자(또는 관리자)가 워크플로우나 위험 등급별로 에이전트의 자율성을 설정할 수 있다. 처음 실행하는 워크플로우에는 낮은 자율성을 기본으로 설정하고, 에이전트가 입증된 신뢰성을 통해 자율성을 얻도록 한다. [Hatchworks](https://hatchworks.com/blog/ai-agents/agent-ux-patterns/) 자율성은 처음부터 고정값이 아니라 사용자가 경험하면서 확장할 수 있는 값이어야 합니다.

**개발 고려사항:** 자율성 레벨별로 어떤 작업이 자동 실행되고 어떤 작업이 승인을 기다리는지를 명확히 정의한 **권한 매트릭스**가 백엔드에서 먼저 설계되어야 합니다.

---

## 페인포인트 6. 멀티 Agent 상태 관리 어려움 → 가시성 인프라 선행 투자

이 페인포인트는 기획·개발자 관점에서만 존재하며, 사용자가 직접 겪기 전에 제품이 이미 실패하는 원인이 됩니다.

**기획·개발 고충:**

멀티 에이전트 시스템 디버깅의 핵심 과제는 다음과 같다: 오류가 긴 멀티턴 대화 깊숙한 곳에서 나타나는 장기 다중 턴 대화, 동적 협업·도구 사용·계획 변경으로 인한 예상치 못한 에이전트 행동, 한 에이전트를 수정하면 다른 에이전트가 고장나는 연쇄 오류, 적절한 추적 없이는 에이전트가 특정 결정을 내린 이유를 이해하기 어려운 불투명한 추론 경로. [Maxim Articles](https://www.getmaxim.ai/articles/agent-tracing-for-debugging-multi-agent-ai-systems/)

구체적으로 개발자들이 겪는 문제:

- Agent A가 Agent B에게 어떤 상태를 전달했는지 추적 불가
- 어느 Agent가 어느 결정을 내렸는지 귀책 불명확
- 상태가 동기화되지 않아 Agent가 이전 맥락을 "망각"하는 문제
- 디버깅 시 전체 실행 이력 재현 불가

**현재 해결 접근:**

LangSmith는 상세한 추적 시각화를 제공한다. 각 에이전트 실행을 중첩된 호출, 도구 실행, LLM 응답이 포함된 추적으로 보여준다. Langfuse는 오픈소스 관찰 가능성 플랫폼으로 세션 추적, 비용 분석, 에이전트 간 핸드오프 추적을 제공한다. [Maxim Articles](https://www.getmaxim.ai/articles/5-ai-observability-platforms-for-multi-agent-debugging/)

**기획 고려사항:** 관찰 가능성(Observability) 레이어는 개발 완료 후 추가하는 것이 아니라, **처음부터 설계에 포함**해야 합니다. 어떤 이벤트를 로깅할지, 어떤 상태를 어떻게 추적할지는 Agent 아키텍처 설계 단계에서 결정되어야 합니다.

## 페인포인트 7. "채팅 우선 설계" 함정 → 아키타입 선행 결정

**기획·개발 고충:** 챗봇 UI 경험을 그대로 가져와서 Agent에 적용하면, Agent가 실제로 필요로 하는 상태 관리·승인 흐름·감사 로그 등이 설계에서 빠집니다. 나중에 붙이려 하면 전체 구조를 다시 설계해야 합니다.

**기획 고려사항:** 섹션 3+7에서 정의한 아키타입 선택이 이 함정을 방지합니다. Use case 유형을 먼저 판정하고 아키타입을 결정한 후 채팅 영역의 비중을 정하는 순서가 핵심입니다. 채팅창을 먼저 만들고 기능을 붙이는 순서와는 반대입니다.
