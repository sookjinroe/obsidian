## Use case 분류 기준

Use case를 분류하는 기준은 두 가지 축으로 설정합니다.

**축 1 — 작업 성격:** 무엇을 하는가 **축 2 — 자율성 수준:** 사람이 얼마나 개입하는가

이 두 축의 교차로 실제 설계 결정이 달라집니다.

---

## Use case 3대 유형과 UI 설계 가이드

MIT AI Agent Index(2025)가 30개 주요 AI Agent 제품의 사용 사례를 분석한 결과, 광고된 사용 사례는 세 가지 주제로 집중된다. 리서치와 정보 합성이 12/30개 Agent에 등장하며 소비자용 챗 보조와 엔터프라이즈 플랫폼 모두에 걸쳐 있다. 비즈니스 기능(HR, 영업, 지원, IT)에 걸친 워크플로우 자동화는 11/30개에서 나타나며 엔터프라이즈 제품에 집중된다. 폼 작성, 주문, 예약 같은 작업을 위한 GUI/브라우저 조작은 7/30개에서 강조된다.

이를 기반으로 S-Core 관점에서 실무에 적용 가능한 3+1 유형으로 재구성합니다.

---

### 유형 A. 정보 조회·분석형 (Research & Synthesis)

**정의:** 사용자가 질문하면 Agent가 여러 소스를 탐색·종합해 인사이트를 제공. 실행은 없고 정보 전달이 목적.

**대표 사례:** Perplexity Finance, Valley AI, 내부 지식 검색 Agent

**UI 설계 가이드:**

|요소|권장 방향|
|---|---|
|주도 화면|채팅 + 결과 패널 병렬 구성|
|투명성|출처·인용 필수 표시|
|컨트롤|검색 범위 설정, 소스 필터|
|결과 형식|텍스트 요약 + 차트/테이블 혼합|
|HITL|불필요 (사용자가 직접 판단)|

**설계 시 핵심 질문:**

- 결과물을 어떤 형식으로 소비하는가? (읽기 vs. 의사결정 재료)
- 출처 신뢰도가 도메인에서 얼마나 중요한가?

---

### 유형 B. 문서·콘텐츠 생성형 (Document Generation)

**정의:** Agent가 사용자의 요구사항과 기존 자료를 바탕으로 문서·보고서·코드 등 결과물을 생성. 사람이 검토·수정.

**대표 사례:** Harvey AI, Cursor, GitHub Copilot

**UI 설계 가이드:**

|요소|권장 방향|
|---|---|
|주도 화면|문서 에디터 or 코드 에디터가 메인|
|투명성|변경 전후(Diff) 시각화, 근거 링크|
|컨트롤|승인/거부/수정 단위 선택 가능|
|결과 형식|편집 가능한 문서 형태|
|HITL|섹션 단위 or 전체 검토 후 적용|

**설계 시 핵심 질문:**

- 사용자가 결과물의 어느 단위까지 수정 권한을 가지는가?
- 조직의 기존 템플릿·스타일가이드를 어떻게 반영하는가?

---

### 유형 C. 프로세스 자동화형 (Process Automation)

**정의:** Agent가 여러 시스템에 걸쳐 다단계 작업을 자율 실행. 사람은 시작 지시와 예외 처리 담당.

**대표 사례:** 외환 컴플라이언스 자동화, 품질 검사 Agent, RPA 대체 Agent

**UI 설계 가이드:**

|요소|권장 방향|
|---|---|
|주도 화면|워크플로우 뷰 + 실행 타임라인|
|투명성|각 단계 실행 상태, 사용 시스템 표시|
|컨트롤|단계별 승인·중단·재시작|
|결과 형식|완료 리포트 + 감사 로그|
|HITL|고위험 분기점에서 명시적 승인 요청|

**설계 시 핵심 질문:**

- 되돌릴 수 없는 작업(전송, 결제, 등록)이 포함되는가?
- 규제·컴플라이언스 요구로 감사 로그가 필수인가?

---

### 유형 D. 메타데이터 추출·구조화형 (Extraction & Structuring)

S-Core AX TF팀의 메타데이터 extractor 데모와 직접 연결되는 유형으로 별도 분류합니다.

**정의:** Agent가 비정형 데이터(문서, 이미지, 로그)에서 구조화된 정보를 추출하고 편집 가능한 형태로 제공. 사람이 결과를 검증·보완.

**대표 사례:** VLM 기반 문서 판독, 계약서 조항 추출, 품질 데이터 수집 자동화

**UI 설계 가이드:**

|요소|권장 방향|
|---|---|
|주도 화면|원본 문서 뷰어 + 추출 결과 패널 병렬|
|투명성|어느 위치에서 추출했는지 하이라이트|
|컨트롤|필드 단위 수정·확정·반려|
|결과 형식|편집 가능한 구조화 테이블 or 폼|
|HITL|신뢰도 낮은 필드는 자동 플래그 + 검토 요청|

**설계 시 핵심 질문:**

- 추출 신뢰도(confidence score)를 사용자에게 어떻게 보여줄 것인가?
- 검토 완료된 데이터를 어느 시스템으로 내보내는가?

## 유형별 UI 구조 비교 한눈에 보기

```
           낮은 자율성 ←————————————→ 높은 자율성
           (사람이 많이 개입)          (Agent가 많이 실행)

정보 조회형  [채팅 + 결과 패널]
    ↓
문서 생성형  [에디터 메인 + Diff 뷰]
    ↓
추출 구조화형 [원본+추출 병렬 + 필드 검토]
    ↓
프로세스 자동화형 [워크플로우 뷰 + 타임라인 + 승인 큐]
```

## 설계 방법론 — 5단계 프로세스

실제 기획 시 사용할 수 있는 순서입니다.

**1단계: Use case 유형 판정** 위 A~D 분류표를 기준으로 해당 Agent가 어느 유형인지 판정. 복합형인 경우 주된 가치 흐름 기준으로 판정.

**2단계: 자율성 수준 설정** "이 작업에서 사람이 반드시 검토해야 하는 지점은 어디인가"를 정의. 되돌릴 수 없는 작업, 규제 대상 판단, 고위험 데이터 접근 여부를 기준으로 설정.

**3단계: 투명성 수준 결정** 페인포인트 섹션의 투명성-과부하 균형 원칙 적용. 고위험·비가역 작업일수록 더 많은 정보를 노출하고, 반복적·저위험 작업은 간소화.

**4단계: 핵심 UI 컴포넌트 선정** 섹션 1에서 정의한 6가지 컴포넌트(상태 표시, 툴 로그, 승인 컨트롤, 감사 로그, 공유 작업물 영역, 멀티 Agent 대시보드) 중 해당 유형에 필요한 것을 선택.

**5단계: 도메인 특화 레이어 추가** 섹션 3의 도메인별 UI 차이를 참조해 금융·법률·개발·제조 도메인의 고유 요구사항을 레이어로 추가.

## S-Core 메타데이터 Extractor 적용 예시

위 방법론을 메타데이터 extractor 데모 화면 설계에 바로 적용하면:

|단계|판단 결과|
|---|---|
|유형 판정|D형 (추출·구조화형)|
|자율성 수준|추출은 자동, 검토·확정은 사람|
|투명성 수준|추출 위치 하이라이트 + 신뢰도 점수 표시|
|핵심 컴포넌트|상태 표시 + 공유 작업물 + 승인 컨트롤|
|도메인 레이어|원본 문서 뷰어 연동, 메타데이터 스키마 기반 폼|
