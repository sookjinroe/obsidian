## 사용자 관점 페인포인트

### ① 불투명한 실행 — "블랙박스" 문제

Agent UI에서 가장 많이 언급되는 페인포인트. Agent가 무언가를 하고 있다는 건 알지만, 왜 그런 결정을 내렸는지 사용자는 알 수 없습니다.

에이전트 시스템은 독립적으로 결정을 내리는데, 이 결정이 사용자에게 보이지 않는 경우가 많다. 사용자가 행동의 '이유'를 이해하지 못하면, 시스템이 기술적으로 정확하더라도 신뢰를 잃게 된다. 사용자 기대와 시스템 출력 간의 사소한 불일치도 심각한 오류처럼 느껴지며, 단 한 번의 설명되지 않은 결정이 장기적인 신뢰를 무너뜨릴 수 있다.

### ② 대기 시간의 불안감 — "멈춘 건지 작동 중인지 모름"

Agent는 장시간 실행되는 특성상 사용자가 진행 상황을 체감하지 못합니다.

멀티 에이전트 AI 시스템의 UX 설계 과제에는 지연과 더불어 투명성 부족이 있다. 사용자가 AI를 '블랙박스'로 인식하면 불신이 따라온다.

### ③ 실수 복구 불가 — "되돌릴 수가 없어"

Agent가 자율적으로 실행한 작업의 결과를 되돌리기 어렵거나, 되돌릴 수 있다는 사실 자체를 UI가 알려주지 않습니다.

Agent가 독립적으로 행동할 때, 사용자는 모든 것을 리셋하지 않고도 빠르게 되돌리거나 방향을 바꿀 수 있는 수단이 필요하다. 실행 취소 옵션 없는 오류는 사용자의 불만을 증가시킨다.

### ④ 인터페이스 낯섦 — "어디서부터 시작해야 할지 모름"

기존 소프트웨어 패턴(버튼, 탭, 메뉴)에 익숙한 사용자에게 Agent UI는 진입 장벽이 됩니다.

에이전트 UI는 기존 소프트웨어 패턴을 따르지 않는다 — 버튼도, 탭도, 그저 프롬프트뿐이다. 사용자는 어떻게, 어디서 시작해야 할지 모르는 경우가 많다. 구조의 부재가 주저함을 만든다.

### ⑤ 통제권 상실감 — "내가 아니라 AI가 결정하는 것 같은 느낌"

자율성이 높을수록 사용자는 주도권을 빼앗긴 느낌을 받습니다.

사람들은 시스템이 독립적으로 행동하고 있을 때도 여전히 루프 안에 있다는 느낌을 받아야 한다. UX 설계는 명확하고 접근 가능한 재정의 메커니즘, 상황에 맞는 조정 가능한 자율성 설정, 고위험 실행에 대한 미리 보기 기능을 제공해야 한다. 비상 정지는 숨겨진 안전망이 아니라 가시적인 보증으로 존재해야 한다.

## 기획자/개발자 관점 페인포인트

### ① Agent 역할 불명확 — "이게 도우미야, 실행자야?"

제품을 만드는 입장에서 Agent의 역할 범위를 정의하지 않으면 사용자와의 기대 불일치가 발생합니다.

제품 디자이너들이 반복적으로 마주치는 세 가지 주요 페인포인트는 불명확한 에이전트 역할, 불안정한 사용자 신뢰, 기존 워크플로우와의 낮은 통합성이다. 이것들은 추상적인 문제가 아니라, AI 기능이 채택되거나 포기되는 결과를 결정하는 일상적인 걸림돌이다.

### ② 멀티 Agent 상태 시각화 어려움

여러 Agent가 협력할 때 누가 무엇을 하고 있는지 사용자에게 보여주는 UI를 설계하는 것 자체가 기술적 난제입니다.

멀티 에이전트 시스템은 LLM이 실행 제어 흐름을 주도하는 구조로, 신뢰성·사용자 신뢰·시스템 이해 가능성에 새로운 도전을 야기한다. 핵심 UX 설계 원칙으로는 기능 발견성, 관찰 가능성과 출처 추적, 개입 가능성이 꼽힌다.

### ③ Human-in-the-loop를 "제품 기능"으로 설계하지 못함

승인/개입 포인트를 엔지니어링 안전망으로만 생각하고, 사용자가 실제로 쓰는 UI로 디자인하지 않는 문제입니다.

Human-in-the-loop는 에이전트 오류를 모니터링하는 수동 작업이 아니라, 설계된 에스컬레이션 경로를 갖춘 제품 UI여야 한다.

### ④ "채팅 우선 설계"의 함정

챗봇 UI 경험을 그대로 Agent에 가져오면, Agent가 실제로 필요로 하는 상태 관리, 로그, 승인 흐름 등이 전혀 담기지 않습니다.

채팅 우선 UX의 문제는 모델이 아니다. 인터페이스가 위임과 감독이 아닌 대화를 위해 설계되었다는 것이다. Agent UX 패턴은 인간-에이전트 관계를 위한 반복 가능한 제품 패턴이다. 여기에는 사람들이 목표를 정의하고, 도구 접근 권한을 부여하고, 실행을 감독하고, 안전하게 복구하는 방법이 포함된다.

### ⑤ 투명성과 정보 과부하 사이의 균형

모든 내부 처리를 다 보여주면 사용자가 압도되고, 아무것도 안 보여주면 불신이 생깁니다. 그 균형 기준이 없다는 것이 현장의 페인포인트입니다.

'올바른 내부 정보 표시'는 단계별 상세도로 상태, 사용된 도구, 데이터 소스, 한계를 의미한다. 모든 것이 기본으로 보일 필요는 없다. 간단한 기준: 고위험 행동, 되돌릴 수 없는 단계, 컴플라이언스 민감 컨텍스트에서 더 많은 세부 정보를 드러낸다.

---

개발자 관점에서는 '상태 관리(State Management)'와 '가시성(Observability)' 확보가 가장 큰 고충이다. 에이전트는 다단계 워크플로우를 수행하면서 끊임없이 내부 상태를 업데이트하는데, 이를 시각화하고 디버깅할 수 있는 도구가 부족하여 장애 발생 시 근본 원인을 파악하는 데 막대한 시간이 소요된다. 특히 여러 에이전트가 협업하는 멀티 에이전트 시스템(MAS)에서는 어떤 에이전트가 어떤 결정을 내렸고, 데이터가 어떻게 전달되었는지를 추적하는 것이 거의 불가능에 가깝다.

또한, 에이전트가 디자인 시스템을 준수하도록 강제하는 것도 어려운 과제이다. AI 에이전트는 이미지를 해석하고 UI를 생성할 수 있지만, 각 세션마다 버튼의 둥글기(Border Radius)나 여백(Padding) 같은 미세한 디자인 규칙을 '망각'하는 경향이 있어 일관된 사용자 경험을 유지하기가 힘들다. 이를 해결하기 위해 매번 시스템 프롬프트에 디자인 가이드를 주입해야 하는 비효율성이 발생한다.
