

## 왜 도메인이 아니라 아키타입인가

같은 금융 도메인 안에서도 Bloomberg ASKB는 기존 Terminal에 임베드된 구조이고, Valley AI는 채팅이 아예 없는 툴 스위트이며, Perplexity Finance는 대시보드 위에 채팅을 얹은 형태입니다. 도메인이 동일해도 제품마다 UI 구조가 완전히 다릅니다.

채팅 전용 접근법의 주요 단점은 흐름과 확장성이다. 대부분의 기존 워크플로우와 분리되어 있다. Cursor나 Windsurf 같은 AI 네이티브 스타트업은 빠른 채택을 위해 사용자가 이미 알고 있는 VSCode 표준 위에 구축해야 했다.

따라서 "어느 도메인인가"보다 "**결과물이 무엇이고, AI는 어디에 위치하는가**"가 UI 구조를 결정하는 실제 기준입니다.

---

## 3대 아키타입 정의

|아키타입|핵심 정의|AI의 위치|사용자 역할|
|---|---|---|---|
|**Chat-first**|대화 스레드가 주 화면이자 진입점|전면|질문자|
|**Dashboard-first**|데이터·시각화·KPI가 화면 중심|사이드카(사이드 패널)|분석자|
|**Workflow-embedded**|AI 전용 화면 없음. 기존 도구에 삽입|보이지 않다가 필요 시 출현|작업자|

많은 agent MCP 사용은 임베드된 에이전트를 통해 이루어질 것이다 — 우리에게 요청하지 않아도 필요에 따라 다른 시스템에서 데이터를 가져오거나 내보내는 방식으로 워크플로우 안에 조용히 녹아든다.

---

## 아키타입 1. Chat-first

대화 스레드가 메인이며, 구조화된 결과물(표, 차트, diff)은 대화 버블 안에 인라인으로 임베드됩니다.

**언제 선택하는가:** 사용자의 주된 행동이 **탐색과 질의**일 때. 결과물이 텍스트 요약이나 인사이트이고, 별도 작업 공간이 필요 없을 때.

**하위 패턴 2가지:**

**(A) 순수 대화형** — 결과가 텍스트와 인라인 컴포넌트로 완결. 대표: ChatGPT, Claude.ai, Perplexity

**(B) 대화 + 결과물 프리뷰 패널형** — 오른쪽에 생성된 결과물(문서 초안, 코드, 리포트)이 실시간 렌더링. 대표: Perplexity Finance(포트폴리오 요약), GitHub Copilot Chat

**Chat-first의 신뢰 UI 패턴:** 인라인 인용(출처 번호 → 원문 클릭), Thought Log(추론 단계 펼치기), 응답 피드백(👍👎)

**한계:** 워크플로우가 아닌 대화를 위해 설계된 인터페이스다. 상태 관리, 권한, 감사 추적 등 Agent가 실제로 필요한 것들을 채팅 창은 잘 처리하지 못한다.

## 아키타입 2. Dashboard-first

데이터 시각화·표·KPI 타일이 화면 중심을 차지하고, AI 채팅은 사이드 패널이나 별도 탭으로 존재합니다. 사용자는 대화 없이도 제품의 핵심 가치를 얻을 수 있습니다.

**언제 선택하는가:** 결과물이 **구조화된 데이터**이고, 사용자가 정기적으로 반복 조회하며, 수치 신뢰도가 비즈니스 의사결정에 직접 연결될 때.

**하위 패턴 3가지:**

**(A) 툴 스위트형(챗 없음)** — AI가 데이터를 처리하는 백엔드 역할만 하고, 사용자 인터페이스는 완전히 구조화된 도구들로 구성. 대표: **Valley AI**(DCF 빌더, 섹터 히트맵, 재무제표 비교표 30개 이상 — 채팅 인터페이스 전혀 없음), LandingLens(바운딩 박스 어노테이션 + 혼동 행렬)

**(B) 대시보드 + AI 사이드카형** — 데이터 화면이 메인, AI 패널이 오른쪽에 상시 존재. 대표: Bloomberg ASKB(Terminal 4분할 + 대화 패널), AlphaSense(문서 뷰어 + Generative Grid), Sight Machine(공장 디지털 트윈 + 에이전트 레이어)

**(C) AI 생성 대시보드형(Generative UI)** — 사용자가 목표를 말하면 AI가 해당 대시보드 자체를 동적 생성. 사용자가 "지역별 영업 성과를 보여줘" 같은 목표를 공유하면 AI Agent가 즉석에서 관련 인터랙티브 대시보드나 차트를 생성한다. 대표: Sight Machine Build(에이전트 신규 기능), Perplexity Labs

**Dashboard-first의 신뢰 UI 패턴:** 문장 단위 인라인 인용 → 1차 출처 클릭 연결, Ground-Truth vs. 예측 이중 오버레이, 임계값 슬라이더가 있는 혼동 행렬

## 아키타입 3. Workflow-embedded

AI 전용 화면이 없습니다. 기존 도구(EHR, IDE, CRM, .docx 편집기) 안에 스파클 아이콘·사이드바·컨텍스트 메뉴로 삽입됩니다. UI는 중간 매개체가 되고, 지능은 뒤에서 작동한다. 사용자는 더 이상 소프트웨어를 사용하지 않는다. 에이전트에게 요청하면 에이전트가 도구들에 걸쳐 작업한다.

**언제 선택하는가:** 사용자가 이미 특정 도구에서 일하고 있으며, 그 맥락을 벗어나는 것 자체가 마찰일 때. 결과물이 기존 워크플로우의 일부(문서, 코드, 케이스 레코드)일 때.

**하위 패턴 4가지:**

**(A) 스파클 아이콘 사이드 패널형** — 기존 화면 오른쪽에 AI 패널이 필요 시 펼쳐짐. 엔터프라이즈 표준으로 수렴 중. 대표: ServiceNow Now Assist(✨ 아이콘 → 크기 조절 가능한 플로팅 패널), Intercom Fin Copilot(인용 노란 하이라이팅 + composer 삽입), Salesforce Agentforce(CRM 레코드 내장 위젯)

**(B) 문서 캔버스 + 듀얼 패널형** — 화면 중앙이 편집 가능한 문서, 오른쪽이 AI 패널. 법률·문서 작업 도메인 표준. 대표: **Harvey AI**(Assistant 채팅 + 번호형 인용 패널), **Ironclad Jurist**(3분할: Logs 패널 + .docx 네이티브 에디터 + 채팅)

**(C) IDE 에이전트 워크스페이스형** — 코드 편집기 위에 Agent 패널이 덧씌워지고, 에이전트 병렬 실행·세션 관리가 가능. 단순 "채팅 옆 코드"를 넘어 에이전트 조율 워크스페이스로 진화 중. 대표: Cursor 3(병렬 에이전트 타일 + 멀티파일 diff), GitHub Copilot Workspace(Task → Spec → Plan → Diff → PR 편집 파이프라인), Devin(4분할 에이전트 데스크 + 세션 타임라인)

**(D) 주변 수집 + 백그라운드 실행형** — AI가 백그라운드에서 데이터를 수집·처리하고, 사람은 결과물만 검토. 녹음 버튼이나 이벤트 트리거가 유일한 UI 어포던스. 대표: **Abridge**(Epic 내장 — 녹음 버튼 → SOAP 초안 + Linked Evidence 오디오 하이퍼링크), Thomson Reuters CoCounsel Skill 갤러리

**Workflow-embedded의 신뢰 UI 패턴:** 색상 코딩 Track-Changes 레드라인, Linked Evidence(클릭 → 원본 위치 하이라이팅), 편집 가능 스펙/플랜 아티팩트, 세션 리플레이 타임라인, 별도 거버넌스 대시보드(AI Control Tower)

## 아키타입 × Use case 매트릭스

아키타입(어떤 구조인가)과 Use case(무엇을 하기 위해 존재하는가)를 교차하면 실제 설계 선택지가 구체화됩니다.

| |**A. 정보 조회·분석**|**B. 문서·콘텐츠 생성**|**C. 프로세스 자동화**|**D. 추출·구조화**|
|---|---|---|---|---|
|**Chat-first**|Perplexity, ChatGPT|ChatGPT, Claude.ai|(드뭄 — 신뢰 문제)|(드뭄)|
|**Dashboard-first**|Valley AI, Bloomberg, AlphaSense|AlphaSense Grid|Sight Machine, LandingLens|LandingLens Review Table|
|**Workflow-embedded**|Fin Copilot, CoCounsel|Cursor, Harvey, Ironclad|Agentforce, ServiceNow, Devin|Abridge, Harvey Vault|

**매트릭스를 읽는 법:**

- 같은 Use case(열)라도 아키타입에 따라 설계가 완전히 달라집니다
- 비어 있는 셀은 "불가능"이 아니라 "현재 드물거나 아직 성숙하지 않음"을 의미합니다
- Chat-first + 프로세스 자동화 조합이 드문 이유: 비가역 실행에 대한 신뢰 구조를 채팅만으로 담기 어렵기 때문입니다

## Use case별 UI 설계 핵심 원칙

### Use case A. 정보 조회·분석형

**주도 화면:** Chat-first 또는 Dashboard-first (도메인 전문성 수준에 따라) **핵심 설계 포인트:** 출처 필수 표시, 소스 범위 필터, 결과물 내보내기(Excel, PDF) **HITL:** 불필요 — 사용자가 직접 판단 **설계 결정 질문:** "사용자가 결과를 읽기만 하는가, 의사결정 재료로 쓰는가?" → 후자라면 Dashboard-first로 이동

### Use case B. 문서·콘텐츠 생성형

**주도 화면:** Workflow-embedded (문서 캔버스 + 듀얼 패널형) **핵심 설계 포인트:** Diff 시각화(before/after), 섹션 단위 수락/거부, 조직 템플릿 연동 **HITL:** 섹션 단위 또는 전체 검토 후 적용 **설계 결정 질문:** "사용자가 결과물의 어느 단위까지 제어권을 가져야 하는가?"

### Use case C. 프로세스 자동화형

**주도 화면:** Workflow-embedded (스파클 아이콘 사이드 패널형 or IDE 에이전트 워크스페이스형) **핵심 설계 포인트:** 실행 타임라인, 단계별 승인·중단·재시작, 완료 리포트 + 감사 로그 **HITL:** 고위험 분기점에서 명시적 승인 요청 필수 **설계 결정 질문:** "되돌릴 수 없는 작업(전송, 결제, 등록)이 포함되는가?"

### Use case D. 추출·구조화형 (메타데이터 Extractor 직결)

**주도 화면:** Dashboard-first (Review Table형) 또는 Workflow-embedded (주변 수집형) **핵심 설계 포인트:** 원본 문서 뷰어 + 추출 결과 패널 병렬, 추출 위치 하이라이트, 신뢰도 점수, 필드 단위 수정·확정·반려 **HITL:** 신뢰도 낮은 필드 자동 플래그 + 사람 검토 요청 **설계 결정 질문:** "추출 신뢰도를 어떻게 표시할 것인가? 검토 완료 데이터는 어디로 내보내는가?"

## 아키타입 선택 가이드 — 3가지 판단 기준

실제 기획 시 아키타입을 결정하는 순서입니다.

**1. 결과물(Artifact)이 무엇인가?** 텍스트 인사이트 → Chat-first 가능 / 구조화 데이터·수치 → Dashboard-first / 기존 문서·코드·레코드 → Workflow-embedded

**2. 사용자가 이미 어디서 일하는가?** 별도 도구 없이 AI와 대화 → Chat-first / 데이터 플랫폼 중심 → Dashboard-first / 특정 소프트웨어(EHR, IDE, CRM) 안 → Workflow-embedded

**3. 비가역 실행이 포함되는가?** 포함될수록 Workflow-embedded의 HITL 컨트롤이 필수. Chat-first만으로는 신뢰 구조를 담기 어려움
