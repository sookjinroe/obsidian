> **"Agent UI는 도구가 아니라 도메인 분석의 결과물이다."**

---

## 시장이 놓치고 있는 것

앞선 조사 결과를 종합하면 현재 Agent UI 시장의 공통 패턴이 보입니다.

거의 모든 Agent가 GPT, Claude, Gemini 모델 패밀리에 의존하고 있어 생태계 전반에 구조적 의존성이 형성되어 있다. 엔터프라이즈 플랫폼은 사용자가 Level 1~2 수준으로 Agent를 구성하지만, 배포된 Agent는 인간 개입 없이 이벤트에 의해 Level 3~5로 작동하는 설계/배포 분리 현상을 보인다.

즉 대부분의 제품이 **모델 성능 경쟁**과 **범용 UI 템플릿 제공**에 집중하는 반면, **"왜 이 도메인에 이 구조가 맞는가"를 설명하는 방법론**은 비어 있습니다.

이것이 S-Core의 진입 공간입니다.

---

## S-Core의 차별화 포인트 — 3가지 레이어

### 레이어 1. 도메인 분석 → Agent 구조 설계

범용 AI 도구들은 모델과 인터페이스를 먼저 제공하고, 고객이 그 안에서 도메인을 맞춥니다. S-Core는 순서를 바꿉니다.

```
[일반적 접근]     모델 선택 → UI 셋업 → 도메인 적용
[S-Core 접근]     도메인 분석 → Agent 구조 설계 → UI 결정
```

섹션 3에서 확인했듯, 금융 도메인은 대시보드 중심, 법률 도메인은 출처 추적 중심, 개발 도메인은 IDE 임베드 구조가 각각 다른 이유가 있습니다. 그 이유는 모델이 결정하는 것이 아니라 **도메인의 의사결정 구조, 리스크 구조, 책임 구조**가 결정합니다.

S-Core Context Framework가 수행하는 도메인 분석이 바로 이 결정의 근거가 됩니다. UI는 분석의 산출물이지, 시작점이 아닙니다.

---

### 레이어 2. 페인포인트 해소를 설계 원칙으로

섹션 5에서 정리한 10가지 페인포인트 중 S-Core가 방법론으로 직접 대응할 수 있는 것은 다음 세 가지입니다.

**① Agent 역할 불명확 문제 → 역할 정의 선행 원칙**

S-Core의 Agent 설계 프로세스는 구현 전에 Agent의 역할, 목표, 경계를 먼저 정의합니다. 이것이 UI 기획으로 이어지면 "이 Agent가 보조자인가, 실행자인가, 조율자인가"에 따라 UI 컨트롤의 위치와 밀도가 달라집니다.

**② 챗 우선 설계 함정 → Use case 유형 선행 판정**

섹션 7에서 정의한 A~D 유형 분류가 이 함정을 방지합니다. 채팅창을 먼저 만들고 기능을 붙이는 것이 아니라, Use case 유형을 먼저 판정하고 그에 맞는 주도 화면을 결정합니다.

**③ 투명성-과부하 균형 없음 → 위험 기반 노출 원칙**

섹션 5와 섹션 2의 조사 결과를 종합한 원칙입니다. 고위험·비가역 작업에는 더 많은 정보를 노출하고, 반복적·저위험 작업에는 간소화합니다. 이 기준을 도메인 분석 결과에서 도출하는 것이 S-Core 방법론의 강점입니다.

---

### 레이어 3. 재사용 가능한 설계 산출물

Harvey AI가 법률 도메인에서, Cursor가 개발 도메인에서 신뢰를 얻은 것은 단순히 기능이 좋아서가 아닙니다. **도메인의 작업 방식에 맞게 설계된 구조** 때문입니다.

S-Core는 프로젝트마다 이 구조를 처음부터 만들지 않고, 반복 가능한 방법론으로 만들어야 합니다.

|재사용 가능한 산출물|내용|
|---|---|
|도메인별 UI 패턴 라이브러리|금융·법률·품질 등 도메인별 검증된 구성 요소|
|Use case 유형별 와이어프레임 템플릿|A~D 유형별 기본 화면 구조|
|HITL 설계 원칙|자율성 수준별 승인 흐름 표준|
|투명성 노출 기준표|작업 위험도별 정보 노출 수준|

이 산출물들이 축적될수록 S-Core의 제안은 "우리가 만들 수 있다"에서 "우리가 이미 알고 있다"로 격상됩니다.

## Sales Kit 관점 핵심 메시지

전무·상무님 보고와 영업 자료에 활용할 수 있는 메시지를 3단계로 정리합니다.

**왜 Agent UI가 일반 AI와 다른가 (섹션 1, 2 근거)** Agent는 대답하는 게 아니라 실행합니다. 실행하는 시스템의 인터페이스는 탐색이 아닌 감독을 위한 설계여야 하며, 이 차이를 이해하지 못한 채 만들어진 Agent UI는 신뢰받지 못합니다.

**왜 도메인 분석이 먼저여야 하는가 (섹션 3, 5 근거)** 금융, 법률, 제조 도메인의 Agent UI가 구조적으로 다른 것은 우연이 아닙니다. 도메인의 의사결정 구조와 리스크 구조가 UI 설계를 결정합니다. 도메인 분석 없이 만들어진 Agent UI는 채팅창에 기능을 붙인 것에 불과합니다.

**S-Core가 줄 수 있는 것 (섹션 4, 6, 7 근거)** S-Core는 고정된 솔루션이 아니라, 도메인 분석 결과를 Agent 구조와 UI 설계로 변환하는 방법론을 제공합니다. 오픈소스 프레임워크(CopilotKit, AG-UI 등)를 활용해 구축 비용을 최소화하면서, 도메인 특화 설계를 통해 사용자가 실제로 신뢰하고 쓸 수 있는 Agent를 만듭니다.

---

## 종합 — 차별화 포인트 한 문장 요약

> S-Core는 Agent를 만드는 것이 아니라, **어떤 Agent를 어떤 구조로 만들어야 하는지 판단하는 방법론**을 가진 파트너입니다.
