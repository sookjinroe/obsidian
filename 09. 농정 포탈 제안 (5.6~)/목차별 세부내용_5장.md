## 5장 검색 체계
좋습니다. "구축방안"이라는 챕터 정체성을 살리려면 검색을 사용자 경험으로 풀어쓰는 게 아니라 **시스템이 어떻게 구성되어 있는가**를 보여주는 게 맞습니다.
#### 1단계 — RFP 요건군 + 본질 정의

| RFP 항목 | 내용                               |
| ------ | -------------------------------- |
| 1)-5   | 포털 통합검색 및 제안룸 검색 이중화 구성          |
| 7)-1   | 통합검색과 제안룸 내 검색 분리, 목적에 맞는 결과 제공  |
| 7)-2   | 사용자 권한·검색 범위에 따른 검색 결과 제한        |
| 2)-3   | 사용자 권한·검색 위치에 따라 접근 가능한 정보 차등 제공 |

**본질**: 두 채널로 분리된 검색이 사용자 권한·메타데이터에 따라 결과를 차등 제공한다. 핵심 구조: **어디서(채널) × 누가(권한) = 무엇이 보이는가(결과)**
### 1단계 — 본질 재정의

**본질**: 검색 시스템이 어떻게 구성되어 있고, 분리·권한·메타데이터 메커니즘이 어디서 작동하는가

**구성 핵심:**

- 검색 진입점 2개 (포털 통합검색 / 제안룸 내 검색)
- 인덱스 2개 (자산 라이브러리 / 제안룸 산출물)
- 검색 쿼리에 권한 + 메타데이터 필터 결합

---

### 2단계 — 본문 컨텐츠

**검색 인덱스 분리로 진행 중 산출물의 외부 노출 차단**

- 자산 라이브러리 인덱스(확정 자산)와 제안룸 산출물 인덱스(작업 중·확정)를 분리 운영합니다
- 인덱스 분리로 작업 중 자료가 포털 통합검색 결과에 노출되지 않아 진행 중 보안성을 확보합니다

**권한 정보를 검색 쿼리에 포함하여 결과 원천 차단**

- 사용자 유형과 등록된 제안룸 정보를 검색 쿼리 조건에 포함하여 인덱스 조회 단계에서 결과 범위를 한정합니다
- 권한 외 자산은 검색 결과에 포함되지 않아 결과 마스킹이 아닌 원천 차단 방식으로 보안을 확보합니다

**메타데이터를 검색 필터로 활용하여 정밀 검색**

- 자산 등록 시 부여된 메타데이터(사업유형·규모·프로젝트 특성, 3장 연계)를 키워드 검색과 조합하여 결과를 좁힙니다
- 두 인덱스 모두 동일한 메타데이터 스키마를 적용하여 검색 일관성을 유지합니다

---

### 3단계 — 형식 결정

**a.** 시각 자료가 본질 → 검색 시스템 아키텍처 도식이 필수. 텍스트만으로는 인덱스 분리·권한 결합 위치 등 메커니즘이 안 보임.

**b.** 도식 구성: 진입점 2개 → 검색 쿼리(권한 + 메타데이터 필터) → 인덱스 2개 → 결과

**c.** 형태 → 도식 (메인) + 텍스트 (메커니즘 설명)

**d.** 슬라이드 최종 구성

- 포털 통합검색: 사용자 유형에 따라 자산 결과 차등
- 제안룸 자산 검색: 사용자 유형에 따라 접근 범위 차등
- 프로젝트 제안룸 내부: 구성원 여부로 접근 자체 결정

**검색 인덱스 분리로 진행 중 산출물의 외부 노출 차단**

- 자산 라이브러리 인덱스(확정 자산)와 제안룸 산출물 인덱스(작업 중·확정)를 분리하여 각 채널이 필요한 인덱스만 조회합니다
- 진행 중인 제안룸 자료는 포털 통합검색 범위에서 제외되어 보안성을 확보합니다

수정: "진행중인 프로젝트 제안룸 중 자료가" → 어색한 표현 정리

---

**권한 정보를 검색 쿼리에 포함하여 결과 원천 차단**

- 사용자 유형과 등록된 제안룸 정보를 검색 쿼리 조건에 포함하여 권한 범위 내 결과만 반환합니다
- 포털 통합검색·자산 검색은 사용자 유형에 따라 결과 범위를 차등 적용하고, 프로젝트 제안룸 내부는 구성원 여부로 접근 자체를 결정합니다

추가: bullet이 없었던 섹션. 채널별 적용 방식까지 담았습니다

---

**메타데이터를 검색 필터로 활용하여 정밀 검색**

- 자산 등록 시 부여된 메타데이터(사업유형·규모·프로젝트 특성)를 필터로 활용하여 사업 특성에 맞는 자산을 정밀하게 검색합니다
- 자산 라이브러리와 제안룸 산출물 인덱스에 동일한 메타데이터 스키마를 적용하여 채널 간 검색 일관성을 유지합니다
